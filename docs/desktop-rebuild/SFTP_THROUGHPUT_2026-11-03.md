# SFTP 吞吐排查与修复（2026-11-03）

用户反馈内网上传和下载均只有约 8.8 MB/s。本轮确认了客户端的窗口和串行读写瓶颈并完成修复；未连接用户的实际内网服务器，不能据本机结果断言该环境的全部瓶颈已消除。

**排查结论**

- 原实现每次处理 512 KiB，拆为 16 个 32 KiB SFTP 请求；整批响应、写入、磁盘同步和数据库检查点完成后，才读取下一块。请求之间有网络往返与存储等待，带宽不能持续占满。
- 文件选择器上传也逐个等待 512 KiB IPC 分块确认，检查点次数随文件大小增长。进度事件已经限制为约每 100 毫秒一次，没有发现人为的 8.8 MB/s 速率限制。
- 原实现本机 OpenSSH 回环双栏下载约 55 MiB/s、上传约 78 MiB/s，说明 8.8 并非固定上限。加入固定响应延迟后，小窗口造成的降速可复现。
- 本机 en0 显示 1000baseT 全双工。这只证明本机网卡协商状态，不证明目标服务器、交换机、代理或跳板链路的带宽。

**变更范围**

- 契约统一定义 2 MiB 分块上限，前端、预加载验证与业务读写使用同一边界；SFTP 保持兼容的 32 KiB 请求，单次读写最多 64 个并发请求。
- 双栏传输和下载只预读下一块，让读取与当前块的写入、同步和检查点重叠。读取缓冲最多为当前块和一个预读块；五路任务上限保持。
- 暂停或失败先等待在途读取结束再关闭句柄。预读数据不进入进度、摘要或确认偏移，只有当前块写入并保存检查点后才确认。
- 远端 WRITE/CLOSE 确认、本地文件同步、SHA-256 前缀、目标冲突检查和暂存文件提交顺序保留。每次确认覆盖的数据由最多 512 KiB 改为最多 2 MiB；仍逐块持久化，没有改为仅内存保存进度。
- 恢复校验、编辑器和目录归档使用相同的有界读取大小。旧检查点的实际偏移与首块长度仍按记录读取，未更改持久化格式。
- SSH 每一跳就绪后设置 TCP_NODELAY，避免请求批次尾部的小包等待 TCP 合并。没有更换加密算法、添加依赖或降低文件校验。

**实测结果**

下表单位为 MiB/s，与当前 UI 的 MB/s 换算方式一致。每项均校验完整 SHA-256；计时包含准备或提交耗时，是单次本机测量，不能代替真实内网验收。

| 32 MiB + 17 字节，Electron → 业务进程 → OpenSSH/数据库 Worker | 修复前 | 修复后 |
| --- | ---: | ---: |
| 双栏下载 | 55.27 | 126.98 |
| 双栏上传 | 78.43 | 150.94 |
| 文件选择器 IPC 上传（含验收摘要耗时） | 41.99 | 47.62 |

合成 SSH/SFTP 服务对每个 READ/WRITE 响应增加固定 40 毫秒延迟，固定 TCP_NODELAY，两种分块在同一次运行中比较。它隔离窗口影响，不模拟完整物理网络或磁盘：

| 分块窗口 | 上传 MiB/s | 下载 MiB/s |
| --- | ---: | ---: |
| 512 KiB / 16 请求 | 5.75 | 5.81 |
| 2 MiB / 64 请求 | 21.07 | 20.35 |

macOS x64 未签名打包应用另测 128 MiB + 17 字节：IPC 上传 1927 ms、双栏下载 768 ms、双栏上传 701 ms，均完成摘要校验；暂停恢复、冲突保护、安全保存、归档和导航保持连接的已有 SFTP 验收也通过。
