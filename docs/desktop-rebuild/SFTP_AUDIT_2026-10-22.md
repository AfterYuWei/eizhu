# SFTP 文件传输检查与常规流程优化

日期：2026-10-22。范围：当前 Electron 实现的上传、下载、跨会话复制、目录传输、暂停恢复和完成确认。

## 结论

代码中存在能够解释“大文件到了 99% 长时间不结束”的确定缺陷：正常传完之后，上传和复制都再次完整读取目标暂存文件并计算 SHA-256。远端上传因此产生一次反向的全文件传输，界面在此期间只显示“正在完成”。这能解释该现象，但没有使用用户的服务器复现，不能断言用户当次停顿只有这一种原因。

上传完成同时是一个等待所有检查结束的同步 RPC，而主进程只等待 30 秒。回读耗时超过 30 秒时，前端会收到“操作结果未知”的超时，业务进程仍继续工作。部分上传读写或提交异常还会留下占用中的任务；最后提交与取消之间也存在状态竞态。

本次按照常见 SFTP 客户端的做法修正：正常传输依赖协议读写确认、关闭确认、文件类型及长度检查和最后的重命名；不再默认重新下载整文件，也不再为了普通覆盖反复读取旧目标内容。内容哈希保留在断点续传和文本编辑器的冲突检查中。

## 常规流程与完成含义

1. 建立 SSH 连接，校验服务器主机密钥，完成认证，打开 SFTP 子系统。
2. 获取源文件和目标目录信息，处理覆盖、跳过、重命名或询问。普通传输使用文件大小、修改时间等元数据检查目标变化。
3. 在目标同目录创建独占的 `.eizhu-*.part` 暂存文件，保留已有正式文件。
4. 复用打开的文件句柄，流式读取、写入。每批最多 512 KiB，拆成最多 16 个 32 KiB 协议请求并发处理；等待整批确认后推进连续偏移和持久检查点。
5. 传输结束后等待文件关闭确认，检查暂存文件仍是普通文件且长度正确，并检查源信息、目标冲突及权限。
6. 将暂存文件重命名为正式目标。覆盖已有远端文件需要服务器支持 OpenSSH 原子替换扩展；不支持时保留原目标并报错。
7. 持久化最终任务状态并发布完成事件。只有这时显示 100%。此前会显示“准备文件”“传输中”“检查文件”或“提交文件”。

WRITE、CLOSE 和 RENAME 都有各自的成功/失败响应。参考 [ssh2 官方 SFTP 接口说明](https://github.com/mscdex/ssh2/blob/master/SFTP.md)。并发请求属于 SFTP 的常规使用方式；本实现选择有界窗口，避免无限缓存和过多待确认数据。

协议写入成功不等于远端物理介质已经同步落盘。当前远端 `sync()` 不执行 fsync 扩展，也不提供正常完成后的独立磁盘内容哈希证明。本地检查点写入前会等待本地文件同步。这些语义不能混称为“全盘完整性校验通过”。

## 各种传输实际如何执行

| 操作 | 数据路径 | 完成后的文件位置 |
| --- | --- | --- |
| 双栏本机上传到服务器 | 业务进程读取本机文件，经 SFTP 写入远端暂存文件 | 远端所选目录 |
| 双栏服务器下载到本机 | 业务进程读取远端文件，写入本机暂存文件 | 本机所选目录 |
| 两个远端会话之间复制 | 远端 A → 本应用的有界内存块 → 远端 B | 远端 B 所选目录 |
| File/Blob 分块上传接口 | 前端流合并为最多 512 KiB，逐批调用领域接口并等待确认 | 目标会话所选目录 |
| 下载暂存接口 | 远端 → 应用私有暂存目录；完成后通过“保存下载文件”另存 | 用户选择的保存位置 |
| 保持目录结构 | 枚举目录，创建目录并按文件传输；逐个文件提交 | 目标目录树 |
| 目录归档传输 | 先流式生成本地归档暂存，再发送归档 | 目标归档文件 |

远端之间复制目前使用本应用中继，不是服务器之间直接发送。归档及下载暂存需要本机临时磁盘空间。目录传输逐文件提交，取消不会回滚已提交文件，也不提供整个目录的原子事务。

## 已修改的问题

| 问题 | 修改 |
| --- | --- |
| 正常结束再次完整回读目标，进度固定停在 99% | 删除正常完成路径的全文件回读，等待 ACK、CLOSE、类型/长度检查和重命名 |
| 覆盖大文件时反复读取旧目标 | 普通传输改为元数据冲突检查；编辑器继续使用内容哈希 |
| 大包内部串行等待响应，延迟累积 | 每路使用最多 16 个 32 KiB 请求，整个窗口最多 512 KiB |
| 上传最终处理挤在 30 秒 RPC 中 | `uploadFinish` 接受后台提交，事件及任务查询返回最终结果 |
| 上传失败占住通道 | 关闭句柄、失效上传 ID、发布失败状态、释放名额并继续调度 |
| 前端错误处理把后端失败改成暂停 | 查询任务状态，仅暂停仍在运行的任务，保留已发生的失败 |
| 取消与重命名并发，可能覆盖已完成状态 | 提交前检查取消信号；提交已经成功则保留完成结果 |
| 恢复时重复读取同一前缀 | 单次读取同时重建摘要并验证检查点 |
| 正在检查、提交阶段被事件节流隐藏 | 阶段转换强制发布事件，界面显示实际步骤 |
| 分块上传速度始终为零 | 根据本次执行已确认字节计算速度 |
| 源文件变化后重新开始，任务总大小未更新 | 重新读取源信息并重算任务大小 |
| 目标打开失败可能泄漏源句柄 | 在受保护的清理范围内打开目标，等待所有已打开句柄关闭 |
| 常见系统错误仅显示笼统失败 | 空间/配额不足、权限不足、连接断开和超时使用安全的中文错误信息 |

普通覆盖检查不会发现“大小、修改时间和其他可用标识均未变化”的外部内容修改。这与元数据检查的能力一致；需要内容级比较的编辑器仍保留 SHA-256 校验。

## 暂停、恢复和限制

- 正常任务最多同时执行五路；普通复制任务排队，File/Blob 上传通道满时返回队列已满。
- 每批全部写入确认后才更新检查点，避免把仅发送但未确认的字节当成已完成。
- 暂停等待正在执行的批次和句柄释放，保留暂存文件；恢复前校验服务器身份、文件属性及已有前缀。
- 取消清理本任务尚未提交的暂存文件。已提交的目录文件保留。
- 业务进程重启后，未完成任务转为待手动恢复；不会自动重放结果未知的写操作。
- 单个远端请求 20 秒未响应时，关闭相应 SFTP 通道并报错；共享该通道的任务可能受影响，需要重新连接后手动恢复。
- 已有前缀的完整校验有真实读取成本。File/Blob 上传的恢复初始化目前仍是同步 RPC，主进程 30 秒超时边界仍适用；本次后台化的是最终提交，不能宣称所有长耗时初始化均已后台化。
- 当前仍逐批写入加密数据库检查点，本地目标也逐批同步；没有证明在高延迟网络或慢盘上能跑满带宽。
